# Eval flywheel plan: replayable behavior checks for Harness Firmware

## Why

Both talks argue that an agent improves only through a loop that turns observed misses into repeatable checks, and that the quality of those checks sets how far the loop can go. The firmware already verifies each task with care, but it keeps no committed, replayable set of behavioral scenarios: every test script in `.claude/scripts/` and every CI step in `.github/workflows/validate-template.yml:56-75` checks structure, and evaluation trial logs stay in gitignored scratch (`.claude/skills/refine/references/evaluation.md:3`). A miss fixed today is never re-run when a later edit touches the same skill.

Sources: W = "How We Built an Agent That Improves Itself" (Zubin Aysola, W&B), https://www.youtube.com/watch?v=XyV6bSMyq-I ; I = "The Loop Is the Product" (Roland Gavrilescu, Introspection), https://www.youtube.com/watch?v=7taOQBfjDyE

### P2. Committed regression scenarios with a user calibration step

- **Type:** add
- **Talk IDs:** W1, W8, I2, I3, I4, I6
- **Touches:** `.claude/evals/` (new), `.claude/evals/README.md` (new), `.claude/skills/refine/SKILL.md`, `.agents/skills/refine/SKILL.md`, `assets/readme/` (the 16 panel SVGs) and `README.md`, both regenerated by `scripts/readme/build.mjs`
- **Design:**
  - Home: one Markdown file per scenario at `.claude/evals/<skill>/<slug>.md`. The folder sits outside the skill folders, so scenario files do not travel with standalone skill installs or into the Codex skill folders.
  - Format: YAML frontmatter with `skill`, `kind`, `origin`, `added`, `calibrated` and `ablate`. `kind` is one of pressure, application, recognition, retrieval, negative or neighboring, the case types `.claude/skills/addskill/references/authoring.md:25-32` already names. `origin` is miss, win or synthetic. `calibrated` holds the date the user agreed with a judged outcome, or `pending`. `ablate` lists every in-repo `path:start-end` span that states the rule under test, kernel copies included. Body sections: `## Setup` (files or state to create in scratch), `## Prompt` (the single instruction the subject agent receives), `## Pass criteria` (3 to 6 binary checks an outsider can verify from actions and artifacts, the arena rule at `.claude/skills/arena/SKILL.md:24`) and `## Failure seen` (a paraphrase of the original miss). No quoted chat, no session file paths, no credentials, per `.claude/skills/refine/SKILL.md:36-39`; the repository is public.
  - Arms: every run happens in a detached worktree created with `git worktree add --detach` under the OS temp directory, outside any folder that holds a `CLAUDE.md`. The subject runs as `claude -p` with that worktree as its working directory, so it loads that arm's kernel and skills and no others from the repo. The main arm checks out `origin/main`. The ablation arm checks out the same commit and deletes every span in `ablate`. User-level files under `~/.claude/` still load in every arm; the run log records a grep of them for the rule, and a hit is listed as a confound.
  - Subject flags: `claude -p --model <session model> --effort <session effort> --restricted --tools "Read,Glob,Grep,Edit,Write,Bash,Skill" --allowed-tools "Bash(node *)" "Bash(git diff *)" "Bash(git status *)" "Bash(git log *)" --permission-mode acceptEdits --permission-prompts none --strict-mcp-config --no-chrome --no-session-persistence --output-format text "<Prompt>"`. Model and effort are the session's own, never `sonnet` or `haiku`. Per `claude --help`: `--restricted` keeps Bash only because `--tools` names it, confines the file tools to the working directory, and ignores user, project and local settings files, so neither the user's hooks nor the project allowlist (which allows `git push` and `gh pr create`) reach the subject; `--allowed-tools` supplies the only command allows, so seeds (a) and (b) can run `node` and seed (b) can read git history; `acceptEdits` lets Edit and Write change files in the arm, which seed (c) needs; `--permission-prompts none` denies anything else that would prompt, so no run waits on input. Slash commands stay enabled, unlike the reviewer flags at `.claude/skills/claude-review/SKILL.md:41-45`, so the arm's skills load. On native Windows, `Bash` becomes `PowerShell` in `--tools` and in each allow rule, per `.claude/skills/claude-review/SKILL.md:48`. Ignoring project settings also drops the project output style and SessionStart hook; the run log lists that as a confound next to the W2 note below.
  - Flag behavior the help text leaves uncertain, settled by the dry run in Acceptance: (1) whether `--allowed-tools` rules apply under `--restricted`, whose help names only managed settings and `--settings` as still applying; (2) whether `--restricted` counts `.claude/reference/pitfalls.md` as a tool-configuration file that only a person may approve, which would deny seed (c)'s edit; (3) whether skills load only when `Skill` is named in `--tools`; (4) whether a `PowerShell(node *)` prefix rule matches as `Bash(node *)` does. If (1) or (2) fails, the fallback drops `--restricted` and adds `--setting-sources project` plus `--disallowed-tools "Bash(git push)" "Bash(git push *)" "Bash(git commit)" "Bash(git commit *)" "Bash(git merge)" "Bash(git merge *)" "Bash(gh pr)" "Bash(gh pr *)"`, so the arm's own allowlist loads without its publish commands, and the dry run repeats with that set. Each command gets a bare rule beside its space-star rule because `.claude/settings.json:59-60` allows bare `git push` in a rule of its own, which a space-star disallow may not match.
  - Repo-side home for the procedure: `.claude/evals/README.md` (new) states that scenario files are durable project files while trial logs stay under `.claude/skills/refine/references/evaluation.md:3`, and it holds the format, the arm setup and the calibration questions. The four `evaluation.md` copies stay unchanged, so a standalone or Codex install never names a folder or script it lacks (`.claude/skills/refine/references/evaluation.md:46`).
  - Trigger for misses: refine's routing sentence (`.claude/skills/refine/SKILL.md:55-59`) gains one conditional destination: in a project that has `.claude/evals/` (new), a failure that passed the three attribution checks (`.claude/skills/refine/SKILL.md:41-50`) and has a reproducible trigger also becomes a scenario per that folder's README. The evaluation record already requires a targeted and a neighboring scenario frozen before trials (`.claude/skills/refine/references/evaluation.md:5`); promotion copies those two into scenario files, so no new authoring step exists. refine is `native` in `.agents/skill-modes.json`, so the implementer mirrors the sentence by hand into `.agents/skills/refine/SKILL.md:63-68`.
  - Trigger for wins: when a refinement's verdict is `VERIFIED`, its targeted scenario is promoted with `origin: win`, so the gained behavior is guarded as well as the fixed miss.
  - Calibration: before commit, the agent shows the user the pass criteria and one judged outcome and asks "do you agree with this verdict?". `calibrated` gets a date only on a yes; on a no, the agent rewrites the criteria and asks again. For `origin: miss` it then asks a second, separate question: "may this scenario be published in this public repository?". A no keeps the file out of the commit; agreement with a verdict never counts as consent to publish (`.claude/skills/refine/references/evaluation.md:15`). A `pending` scenario can run but is reported apart from calibrated ones.
  - Seeds: three synthetic scenarios drawn from rules the firmware already states, so the format is exercised before any real miss. (a) refine negative case: truncated tool output explains the failure, and the correct outcome is zero instruction edits (`.claude/skills/refine/SKILL.md:41-50`). Its Setup builds a synthetic transcript directory in the arm's scratch space and its Prompt passes it through `--project-dir` (`.claude/scripts/memory-audit.mjs:16-19`), so the subject never reads real session history; `ablate` is the whole three-check paragraph. (b) long-horizon auditor case: the executor edited the gate it reports as passing and did not disclose the edit in its report; the criterion is an integrity verdict other than `clean` (`suspect` or `violation`), since the rule says `suspect` at best and defines no separate threshold for `violation` (`.claude/skills/long-horizon/SKILL.md:129-133`). (c) recall case: a confirmed quirk that cost a retry is saved to pitfalls without asking; `ablate` holds both `.claude/skills/recall/SKILL.md:20-23` and the kernel copy at `CLAUDE.md:87`.
- **Acceptance:**
  - Dry run first, before any seed is judged: in a main arm, one `claude -p` subject with the subject flags above, given a fixed probe prompt, runs `node .claude/scripts/memory-audit.mjs --project-dir <synthetic dir>` and a `node` done-check, runs `git diff`, edits `.claude/reference/pitfalls.md`, writes a new file, invokes one skill, and attempts `git push`. The process exits 0 without waiting on input; the node output, the `git diff` output, the pitfalls edit, the new file and the skill's first action are each present as artifacts in the arm; the push is denied. The probe alone runs with `--output-format json` in place of `text`, and the push counts as denied only when the result's `permission_denials` list names the `git push` call; a git error in the output (detached HEAD, no upstream, rejected ref) means the command ran, and the probe fails. A failed probe switches to the fallback set and repeats before any seed runs. If the fallback probe also fails, P2 stops: no seed runs, and the agent records the failing check and its output as a new open question for the user.
  - `.claude/evals/` (new) holds the three seeds across three skills, each with every frontmatter field, 3 to 6 pass criteria, and `calibrated` set from the user's answer.
  - Each seed, run in a main arm, passes every criterion as judged by a separate fresh agent that sees only the criteria and the raw artifacts. Each seed also fails at least one criterion in its ablation arm; a seed that still passes there does not test its rule and gets rewritten.
  - Results go in the PR body. The body is written to a `.tmp/` file and passes the privacy grep below before `gh pr create --body-file`.
  - `node .claude/scripts/sync-codex-skills.mjs --check` and `node .claude/scripts/test-codex-contract.mjs` pass; `node scripts/readme/build.mjs` has been run and `node --test scripts/readme/readme.test.mjs` passes (a `SKILL.md` edit stales the README panels, `.claude/reference/pitfalls.md:120-129`).
  - A grep over `.claude/evals/` (new) and the PR body file finds no session UUIDs, no home-directory paths and no `.jsonl` names.
- **Size:** M. One skill sentence mirrored across runtimes, one README and three calibrated seeds with ablation runs; no code.
- **Depends on:** none

### P3. Scenario lint and change-scoped replay

- **Type:** add
- **Talk IDs:** W1, W4
- **Touches:** `.claude/scripts/eval-scenarios.mjs` (new), `.claude/scripts/test-eval-scenarios.mjs` (new), `.github/workflows/validate-template.yml`, `.claude/evals/README.md` (new)
- **Design:**
  - A dependency-free Node script with three modes, in the style of `.claude/scripts/memory-audit.mjs`.
  - `--check` (default): parse every scenario file, skipping `README.md`. Fail, naming the file, when the skill has no folder in `.claude/skills/`, a frontmatter field is missing or outside its allowed values, an `ablate` path does not exist, the criteria count is outside 3 to 6, or the body matches a privacy pattern (UUID, drive-letter or home-directory path, `.jsonl` name). `--check-file <path>` applies the privacy patterns alone to any text file, such as a PR body. CI runs `--check` as a new step after the Codex steps in `.github/workflows/validate-template.yml`. It makes no model calls, matching every existing CI step.
  - `--affected <base>`: list changed paths with `git diff --name-only <base>` (working tree against base, so uncommitted edits count) plus `git ls-files --others --exclude-standard`, and map paths under `.claude/skills/<name>/` or `.agents/skills/<name>/` to the scenarios for that skill. A `CLAUDE.md` or `AGENTS.md` change selects nothing by default; `--all` selects every scenario on request. For each selected scenario, create the two arms as P2 defines them: base is a detached worktree at `<base>`; candidate is a detached worktree at `<base>` with `git diff --binary <base>` applied and the untracked files copied in, so it matches the working tree whether or not the edit is committed. Write `.tmp/evals/<run-id>/<slug>/brief.md` (Setup and Prompt only) and `.tmp/evals/<run-id>/judge/<slug>.md` (Pass criteria), so the subject never sees the criteria, the same blinding arena uses (`.claude/skills/arena/SKILL.md:24`). Print the arm paths, the scenario count and the agent-run count: two arms times subject plus judge is four runs per scenario.
  - Running stays with the session agent, not the script. It launches each subject with `claude -p` from the arm directory as P2 defines, then a fresh judge that returns pass or fail per criterion with evidence. Comparison rules come from the evaluation record unchanged: fingerprint baseline, candidate and evaluator; same model, tools, inputs and budget (`.claude/skills/refine/references/evaluation.md:5-7`). Teardown runs `git worktree remove` on the arms this run created and deletes `.tmp/evals/<run-id>/`, after verdicts are in the PR body.
  - Scope: replay runs only for skill edits that already need trials under `.claude/skills/refine/SKILL.md:65-67` (material changes to routing, decisions, verification or retained behavior). Wording and metadata fixes on the static-validation path skip it.
  - Report, not gate: the PR body lists each calibrated scenario that passed on base and failed on the candidate under a `Regressions` heading; `pending` scenarios appear under their own heading. Nothing blocks the merge mechanically: CI makes no model calls and `gh pr merge` does not block on a red check here (`.claude/reference/pitfalls.md:128-129`). The merging agent reads the heading; open question 4 asks whether to enforce it.
  - The replay procedure and its scope go into `.claude/evals/README.md` (new), not into `evaluation.md`.
- **Acceptance:**
  - `node --test .claude/scripts/test-eval-scenarios.mjs` covers: a valid fixture passes; a missing field, 7 criteria, an unknown skill, a missing `ablate` path and a UUID in the body each fail with the file named; `--check-file` flags a UUID in a plain text file; `--affected` maps an uncommitted change to `.claude/skills/refine/SKILL.md` to refine scenarios only, maps a changed `CLAUDE.md` to none and `--all` to every scenario; the candidate arm contains the uncommitted edit and the base arm does not; no brief file contains any pass-criteria text.
  - The new CI step runs and passes on the PR (`gh pr checks <n>`).
  - A dry run with an uncommitted edit to the refine skill lists the refine seed from P2, writes its brief and judge files, creates both arms under the OS temp directory, and leaves no arm behind after teardown (`git worktree list`).
- **Size:** M. One script of roughly 250 lines, its test file, one CI step and a README section.
- **Depends on:** P2

### P4. Failure-pattern and token-cost sections in memory-audit

- **Type:** improve
- **Talk IDs:** I5, I8, W8
- **Touches:** `.claude/scripts/memory-audit.mjs`, `.claude/scripts/test-memory-audit.mjs` (new)
- **Design:**
  - Scan filter: today the loop skips every line lacking `"tool_use"` (`.claude/scripts/memory-audit.mjs:152`), which drops both the `tool_result` lines and the assistant `usage` this item needs. The prefilter widens to lines containing `"tool_use"`, `"tool_result"` or `"usage"`, and the existing read counting keeps its own content check.
  - Failure patterns: collect `tool_result` blocks with `is_error: true`, build a signature from the tool name plus the first line of the result with digits, hex ids, quoted strings and paths replaced by placeholders, and print the 5 signatures that occur in the most sessions (minimum 3 sessions), each with its session count and the skills invoked in those sessions. Also count, per invoked skill, the sessions where a user turn matches refine's standing-rule phrases (`.claude/skills/refine/SKILL.md:21-25`). Output holds counts and signatures only, never user text or session paths (`.claude/skills/refine/SKILL.md:36-39`).
  - Token cost: Claude Code writes one line per content block and repeats the same `message.id` and `usage` on each, so the script keeps one `usage` per `message.id` (falling back to `requestId`) before summing. It sums `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` and `output_tokens` per session, kept as separate fields because cache reads dominate and bill at a different rate. It attributes a session's totals to each skill invoked in it and prints per skill: invocations, sessions, median output tokens and median uncached input per session. The value side stays the invocation count, plus the scenario count per skill when `.claude/evals/` (new) exists. The report labels attribution as session-level and approximate.
  - No skill edit: refine already runs this script (`.claude/skills/refine/SKILL.md:14`). A signature is a candidate only; refine's three attribution checks decide whether it becomes a P2 scenario.
  - Order: P4 needs only P1 but ranks after P3. Its signatures pay off only as P2 scenarios that P3 replays on later edits, and its value column counts scenarios per skill, which stays empty until P2 lands.
- **Acceptance:**
  - `node --test .claude/scripts/test-memory-audit.mjs` gains fixtures: three sessions with the same error, differing only in paths and numbers, collapse into one signature; one message split across three lines with the same `message.id` and `usage` counts once, and `usage` fields sum per field across distinct ids; the output contains none of the fixture's user text or file names.
  - `--json` output adds `patterns` and `cost` keys; existing keys are unchanged.
- **Size:** M. Two report sections and a filter change in one script plus fixtures.
- **Depends on:** P1

### P5. Simulated-user scenarios for multi-turn behavior

- **Type:** improve
- **Talk IDs:** W6
- **Touches:** `.claude/scripts/eval-scenarios.mjs` (new), `.claude/scripts/test-eval-scenarios.mjs` (new), `.claude/evals/` (new), `.claude/evals/README.md` (new)
- **Design:**
  - Optional `## Persona` section in a scenario: the user's goal, what they know, what they will and will not volunteer, when they correct the agent, and a stop condition. Frontmatter `turns` caps the exchange at 6 or fewer.
  - The session agent relays: the subject receives the Prompt through `claude -p` in its arm as P2 defines, with session persistence on and `--output-format json` so the session id is captured; each subject reply goes to a fresh persona agent that answers in character; the session agent sends the answer with `claude -p --resume <session-id>` from the same arm directory so the subject's context persists. The exchange ends at the stop condition or the turn cap. The judge receives the full exchange and the criteria. The persona agent follows the same model floor as every other agent. Teardown also deletes the transcript folders these runs created under the temp-path project names.
  - Targets: behaviors a single prompt cannot test. refine's "The user said opposite things: Ask" row (`.claude/skills/refine/SKILL.md:33`) and fable-mode's ask-or-continue rule (`.claude/skills/fable-mode/SKILL.md:19-20`).
  - The relay procedure goes into `.claude/evals/README.md` (new) next to the replay procedure.
- **Acceptance:**
  - `--check` accepts a persona scenario and rejects `turns` above 6 and a persona without a stop condition; the test file covers both.
  - A resumed `claude -p` turn recalls a fact given only in the first turn.
  - One calibrated persona scenario per target passes in a main arm as judged by a fresh agent, and each fails at least one criterion in its ablation arm.
- **Size:** M. Format extension and relay procedure are small; most effort goes into writing personas the judge can score.
- **Depends on:** P2, P3

## Rejected / deferred

- W2 (byte-identical research and production code): partly covered. Arms load the same kernel and skill files a session in that checkout loads, and Claude-to-Codex drift has a CI gate in `.github/workflows/validate-template.yml:56-63`. The prompt stack is not byte-identical: a `claude -p` subject runs without the interactive session's history, re-injected output style and live user, and a subagent would differ further (`CLAUDE.md:19`). Each replay records this as a confound, and behaviors that depend on the output style, such as caveman's switch to normal prose on user confusion (`.claude/skills/caveman/SKILL.md:14`), are not replay targets.
- W3 (declarative variants, many parallel runs): deferred. The two-arm comparison in `.claude/skills/refine/references/evaluation.md:5` and arena's three candidates (`.claude/skills/arena/SKILL.md:33`) cover current needs; an N-variant runner multiplies floor-model agent runs by N per scenario. Revisit when a change has 3 or more competing wordings and the suite holds 10 or more calibrated scenarios.
- W4 (hydrate, run, score, teardown pipeline): partly adopted in P3 as scratch arms, blinded briefs and owned-worktree teardown. The plan rejects a remote environment hydration step: there is no remote environment in a per-developer harness.
- W5 (normative and relative scoring): covered by binary checks and blind A/B judges that do not gate alone (`.claude/skills/wow-loop/SKILL.md:21` and `.claude/skills/wow-loop/SKILL.md:121`).
- W6 (categorized task set of 886 reviewed tasks): the persona part is P5 and the category field is P2's `kind`. The plan rejects a volume target: one developer's misses arrive a few at a time, and each scenario costs four agent runs to replay.
- W7 (effort on scoring robustness and drift): covered by `.claude/skills/refine/references/evaluation.md:5-7` and `.claude/skills/long-horizon/SKILL.md:129-133`. P3 inherits these rules instead of restating them.
- W8 (unattended self-review of rollouts): the trace-to-task link is adopted in P1, P2 and P4. The plan rejects an automatic loop that edits skills on its own: auto-selection does not authorize edits (`.claude/skills/refine/SKILL.md:52-54`), and every replay bills the user.
- W9 (automation does not absolve the human): covered by authorization boundaries across skills; P2's calibration and publish questions keep the user on each verdict that reaches a PR.
- I1 (signal and verifier quality): covered by `.claude/skills/fable-mode/SKILL.md:34-45` and `.claude/skills/long-horizon/SKILL.md:120-128`. The missing measurement of verifier agreement is P2's calibration step.
- I2 (loop-one artifacts feed loop two): partly adopted in P2, since committed scenarios cross worktrees. The plan defers making long-horizon, arena and wow-loop state readable across worktrees: that state is task-specific, and pitfalls plus scenarios carry the durable part.
- I3 (distillation map): two of three routes exist in `.claude/skills/refine/SKILL.md:55-59`; P2 adds the failure-to-eval route.
- I4 (versioned agent recipe): the firmware is the recipe for tweaks and taste; P2 adds the evals leg. Nothing else adopted.
- I5 (cluster traces for uncodified patterns): adopted in P4 as signature grouping. The plan rejects embedding-based clustering: it needs a model call or a dependency, and a few hundred local sessions group well by error signature.
- I6 (agents build judges, human calibrates): adopted in P2.
- I7 (promote diffs after offline evals and a production A/B or bandit): offline half covered by `.claude/skills/refine/references/evaluation.md:11-15`. The plan rejects a production A/B: one developer's sessions are few, varied and unrepeatable, so a bandit would not converge and would run a worse skill on real work.
- I8 (valued work per watt): token cost adopted in P4. The plan rejects energy per task: nothing local measures it, and tokens are the available proxy.
- I9 (portable taste): covered by refine's evidence table and the Codex and starter sync paths (`.claude/scripts/sync-codex-skills.mjs`, `.claude/skills/sync-starter/SKILL.md`).

## Open questions

1. Should `.claude/evals/` (new) ship to spawned projects? The proposal treats it as template-only, but P2 makes no bootstrap change until this question is answered. A "yes, template-only" answer adds `.claude/evals/` (new) to four mirrored lists that must stay in sync: `TEMPLATE_ONLY_PATHS` in `bootstrap/new-claude-project.sh` (sync note at `bootstrap/new-claude-project.sh:27-28`), `$script:TemplateOnlyPaths` in `bootstrap/NewProjectCore.psm1` (sync note at `bootstrap/NewProjectCore.psm1:10-11`), the potential template-only paths in `.claude/skills/init-project/references/profiles.md:51-53`, and the same list in its native Codex copy `.agents/skills/init-project/references/profiles.md:49-51`. Shipping it instead gives spawned projects scenarios for skills they may later change locally.
2. Privacy of miss-derived scenarios: the repository is public, and P2 asks a separate publish question for each `origin: miss` scenario. Where should a scenario the user declines to publish live: nowhere (discarded after the refinement), in `.tmp/` on one machine, or in a private location such as a private companion repository?
3. Replay budget: at four agent runs per scenario, how many may P3 run per PR before asking? The proposal asks above 5 scenarios (20 runs).
4. Should a calibrated regression be enforced at merge, or stay a PR-body report as P3 proposes? Enforcement would mean one line in codex-review's merge-readiness step (`.claude/skills/codex-review/SKILL.md:144`, line 150 on main after #152) that treats a non-empty `Regressions` heading as not ready unless the user waives it.
5. Should P1 and P4 also mine Codex rollouts, which the native Codex refine already reads (`.agents/skills/refine/SKILL.md:39-47`), and worktrees created by other tools, whose munged directory names do not share the repo prefix?
6. Build P5 now, or wait until P2 and P3 have caught at least one real regression?

## Constraints

- After any skill edit, run `node .claude/scripts/sync-codex-skills.mjs --write` and its `--check` mode, and commit the result. Generated adapters are never hand-edited (`CLAUDE.md:93-96`); the refine Codex copy is a native file and gets the same edit by hand.
