# Improve the working process

Inspect actual task events and the relevant current instruction before recommending a change. Separate stale facts, missing guidance, a badly scoped trigger, tool/config defects, and simple failure to follow an existing rule.

A user correction is evidence to examine, not automatically a new universal preference. If the rule already exists, avoid duplicating it. Prefer fixing a small tool defect over documenting a workaround when that fix is in scope.

For a review request, report the evidence and proposed narrow change. For an explicit instruction to improve the workflow, make reversible changes within the named scope. Auto-selection at task end does not authorize global skill edits or publication. Read before editing, preserve unrelated changes, and keep a backup or diff for non-Git files.

Use static validation for straightforward wording/metadata fixes. For a complex decision workflow, evaluate realistic scenarios in fresh context when tools and authorization permit; test neighboring cases as well as the original failure. Judge observable actions, not copied headings. Do not force an agent failure before every small correction.

Report changed files, verification and remaining limits. Zero changes is valid. Commit, push, cross-project synchronization and new paid review runs require the user's existing or explicit authorization, not a one-friction/one-commit rule.
